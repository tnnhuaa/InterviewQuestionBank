## Slide 009 — When Things Go Wrong

_PDF page 2, handout panel 3_

```text
When Things Go Wrong
• Would using some of your

iteration slack help?
• Is there an engineering task that

you can simplify or postpone?
• Reduce the scope: split or remove a story.
• Always stay in control of your iteration, even if you have to
change your plan to do so.
• Any iteration that delivers all of the stories in the current
plan—even if you changed the plan—is a success.
• Under no circumstances, however, should you change the
iteration deadline.
```

## Slide 014 — Don't Get Protective Over Code

_PDF page 3, handout panel 2_

```text
Don't Get Protective Over Code
• Once you write code and check it in to source control, it's no
longer 'your' code, it's the team’s.
• Any team member has the right to change any of the team’s
code.
• Under NO circumstances should you arbitrarily change it back
without a discussion.
```

---

## Slide 015 — Technical No-No's

_PDF page 3, handout panel 3_

```text
Technical No-No's

• Don't do partial check-ins.
• Run all unit tests before checking in.
• Don't change foundational technology or source code
structure without discussion.
• Don't add new technology dependencies to source code
without discussion.
• Nothing you do should ever stop other developers from
working.
• Don't make anyone’s life difficult.
```

## Slide 029 — Reports to Avoid

_PDF page 5, handout panel 5_

```text
Reports to Avoid
• Source lines of code (SLOC) and function
points
– Reporting SLOC encourages defects and high
costs.
• Number of stories
• Velocity
– Never compare velocity across teams.
• Code quality (cyclomatic code complexity)
– They are a useful tool for developers but
they’re too ambiguous for reporting to
stakeholders.
```

## Slide 030 — Reporting Guidelines

_PDF page 5, handout panel 6_

```text
Reporting Guidelines
• Appropriate reporting will help

stakeholders trust that your team is doing good work.
• Over time, the need for reports will decrease,

and you will be able to report less information less frequently.
• Time spent on reports is time not spent developing.
• Technically speaking, reports are wasteful because they don’t
contribute to development progress.
• To avoid creating reports manually, use the iteration demo,
planning boards, and the burn-up chart as only reports
whenever possible.
```
